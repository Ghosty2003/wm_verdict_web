# WM-Verdict Annotation Site

An online annotation site for friends / reviewers: GitHub Pages (static frontend) + Supabase (login and annotation storage) + Dropbox direct links (image hosting).
Each round samples **1/10 (5 units)** by seed from the 50 units of each (model × task × perturbation level); the sampling seed is recorded in the database.

## Architecture

```
Browser ── GitHub Pages (index.html, fully static)
   │  supabase-js (anon key + RLS)
   ├── Supabase: Auth login (email allowlist) · rounds/cards/annotations tables
   └── Dropbox direct links: card images and reference images (dl.dropboxusercontent.com, <img> hotlinking)
```

- Annotation permissions are enforced by database Row Level Security: an account not on the `allowed_emails` allowlist sees nothing after logging in.
- One annotation per person per card (can be edited/overwritten); multiple people annotate the same card, so inter-annotator agreement (κ) can be computed.
- Card order, sampling, questions and label sets are all generated by `tools/make_round.py` from the spec; the web page contains no labeling-criteria logic.

## One-time deployment

1. **Supabase**: create a free project → in the SQL Editor run all of `supabase/schema.sql`
   → in the Table Editor add the invited emails to `allowed_emails`
   → (optional) Authentication → Providers → Email: turn off "Confirm email" to skip email verification.
2. **Frontend**: put the Project URL and anon key from Settings → API into `config.js`, push.
3. **GitHub Pages**: repo Settings → Pages → Source: branch `main`, `/ (root)`, save.
   URL: `https://ghosty2003.github.io/wm_verdict_web/`.

## Publishing an annotation round (on the NAS)

Prerequisites: result images have been synced by the Dropbox backup (`dropbox_backup.sh`), and `~/bin/rclone` has `dbx:` configured.

```bash
export SUPABASE_URL=https://xxx.supabase.co
export SUPABASE_SERVICE_KEY=...   # service_role key, server-side only, never commit it to this repo
python tools/make_round.py --name round1_xxx --seed 20261115 --spec specs/round1.json --dry   # preview the sample first
python tools/make_round.py --name round1_xxx --seed 20261115 --spec specs/round1.json         # write to the database
```

For the spec file format see the comment at the top of `tools/make_round.py` (one entry per cell: unit source jsonl, card image directory, reference image, question, label set).

## Exporting annotations

Supabase SQL Editor:
```sql
select c.model, c.task, c.family, c.level, c.unit_id, a.email, a.label, a.note, a.updated_at
from annotations a join cards c on c.id = a.card_id
where c.round_id = <round id> order by c.sort_key, a.email;
```
Or export CSV directly from the Dashboard. After exporting, feed it into the `agent_human_agreement.py` pipeline to compute agreement.

Script export (read-only, no emails, used for the optimism-rate report): `SUPABASE_SERVICE_KEY=... python3 tools/export_round_annotations.py --round-id 3 --out <file>`.

## Page flow (v4 since 2026-11-16: 5 groups per level, no longer aligned by seed)

- One page = group g (g = 1–5) of one task × perturbation level: same task, same perturbation level, each of the four models (LingBot-VA / OpenWAM-α / Cosmos Policy / UVA) shows one of its own closed-loop runs, one model per row. The models' initial conditions / seeds are not required to match, and seeds are not shown on the page.
- Each row has two areas: REAL (closed-loop real frame strip, round 2 cards) + IMAGINED (imagined last frame, round 3 cards), matched by unit_id; an imagined frame is shown only if it comes from the same run as the real frames, otherwise it is marked "none" and no question is asked.
- Unit selection: for each model, "complete" units (real frames + imagined frame from the same run) are preferred; complete old units already on v3 pages stay in their original group slot; units with only real frames are used as filler only when fewer than 5 complete ones are available. Rules are in the header of select_pages.py.
- The page table is `data/samecase_pages.json` (which cards go on which page), generated by the scripts in `wm_verdict/libero/out/annotation/samecase_20261115/`:
  inventory.py (per-unit inventory of the four models, marking run source and completeness) → select_pages.py (picks 5 per cell per model, deterministic ordering) → build_cards.py (renders images + page table + DB insert manifest; LingBot latents decoded on CPU) → check_pages.py (spot-checks pages + same-run check over the whole table) → check_real_consistency.py (real-frame success/failure consistent with the records).
- v5 (2026-11-17): pages identical to v4; only adds imagined last frames for 351 Cosmos Policy T2/T3 units (T2: 198, T3: 153) whose REAL card was already on the page and whose IMAGINED slot was previously "none". Each is the last window of the last planning call of the same original execution, recomputed with one model call on the archived original input of that planning call (input hash checked); for 22 of the 351 an existing last-window output was reused without new inference. Predicted actions were compared with the recorded executed actions: for 44 units all 16 actions could be compared, for the other 307 only the executed prefix (the original episode ended early). Script `v5_cosmos_imag.py`, stats `v5_stats.json`.
- v6 (2026-11-17): LingBot-VA rows completed from closed-loop reruns. (a) The 660 LingBot rows that had a REAL card but no IMAGINED card (T0: 285, T1: 285, T3: 45, T4: 45) were rerun (568 on an H100 machine, 92 on the RTX 5090 cluster); (b) the 25 B0 pages (5 per task), whose LingBot row was empty, now show 25 LingBot B0 runs (RTX 5090 cluster; per task the first 5 (anchor, seed) pairs of the LingBot Bg2 units, run in the B-family rig with no corruption; LingBot B0 is not a cell of the main results table). Because a unit's real outcome and its imagined frame must come from the same run, both the REAL card and the IMAGINED card of these 685 rows are rendered from the rerun's own npz (same frames and decoding as existing LingBot cards); the old REAL cards of the 660 rows are no longer shown on the pages. Each rerun ran two bit-identical passes; pass 1 is used throughout. The REAL card shows the rerun's own outcome, which can differ from the original record: of the 660 replaced rows, 37 changed outcome (T0: 11 success→failure, 3 failure→success; T1: 14 success→failure, 9 failure→success; T3/T4: none). New cards use new unit_ids (`<unit_id>__h100` for H100, `<unit_id>__cl5090` for the 5090 cluster), so old cards and their annotations stay in the database untouched. All other rows and pages are identical to v5. Script `v6_lingbot_reruns.py`, stats `v6_stats.json`, replaced cards `v6_replaced_cards.tsv` / `v6_removed_cards.tsv`.
- v7 (2026-11-20): UVA rows from the web-native closed-loop reruns. All 1525 UVA page slots were rerun by the UVA teammate in one run (RTX 5090 cluster; every unit replans each step and saves the native imagined video of the same model call whose first action is executed). A unit is used only if its completion record says real frames and prediction come from the same run and action and video from the same model call (1525 of 1525 passed; 0 skipped). Both the REAL card (13 evenly spaced frames from the run's own real frames, final frame boxed) and the IMAGINED card (last imagined frame of the last planning call) of every UVA row now come from that same run. (a) The 1075 UVA rows that had an old REAL card show the rerun instead; the old REAL cards are off the pages but stay in the database with their annotations. Of these, 7 changed outcome vs the old card (T2: 2 failure→success; T3: 1 failure→success, 4 success→failure). (b) The 450 previously blank UVA cells are filled: O (125, occlusion of the FIRST planning input only, black centred square), Bg/Bf/Bz (225, corruption applied to every frame the model reads), F (75, one black main-camera frame at the planning call at env step 60/160/260; 33 runs succeeded before the trigger and are kept as is), T1 K9 / T2 K9 / T3 K8 / T3 K9 / T4 K9 (25, push right after env step 260; 19 succeeded before the push). New cards use new unit_ids (`<unit_id>__webnative`). All other rows and pages are identical to v6. Script `v7_uva_webnative.py` (idempotent: re-running it adds only newly finished units), stats `v7_stats.json`, replaced cards `v7_replaced_cards.tsv`.
- Navigation: the first dropdown selects task × level, the second selects Group 1–5; ←/→ moves between groups, and past the end continues to the next level. The progress bar counts questions. Keys 1–4 answer the currently highlighted (first unanswered) question.
- Inserting new cards: `SUPABASE_SERVICE_KEY=... python3 tools/add_samecase_cards.py --manifest <manifest_samecase.json> [--yes]`, inserts into the existing round 2 / round 3; unit_ids already in the database are skipped (old cards and old annotations untouched).
- Export: `SUPABASE_SERVICE_KEY=... python3 tools/export_samecase.py --out <file> [--cutoff <launch time>]`; annotations on the same-case pages and old annotations go into two separate tables.
- Archive of the page before the redesign: `wm_verdict/libero/out/annotation/samecase_20261115/index_before_samecase_20261115.html`.

## Labels and current coverage (v7)

- Questions: REAL — "Did the real execution complete the task? (judge the boxed final frame)"; IMAGINED — "Does the imagined frame show the task completed?". Labels for all cards on the same-case pages (from the insert manifest): `looks_success` / `borderline` / `not_success` / `uncertain` (keys 1–4); an optional note can be added.
- Analysis convention (not shown on the page): an imagined frame whose task state is complete but which shows visible generation distortion counts as `borderline`.
